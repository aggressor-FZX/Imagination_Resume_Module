# Correction, 2026-11-02 (later the same day): item 4 was wrong

Item 4 above said "Multi-file is untested end to end." It then became "multi-file cannot
capture at all", which was an inference from an endpoint the website never calls. Both
statements are withdrawn. The tag and this manifest stay; only the claim changes.

## What is actually true

`docs/ROUTE_MAP.md` was already correct, and is now backed by execution rather than by
line numbers:

```
frontend  processMultiFileRealAnalysis   src/services/analysis.ts:602
   -> POST {apiBaseUrl}/api/analysis/multi-file?stream=1
orchestrator  server.cjs:3847
   -> POST {imagBase}/analyze            (exactly once, regardless of file count)
Imaginator  app.py:1499  analyze_resume  -> _analyze_resume_impl
   -> source correction + preservation + live_capture.start
```

Evidence: `Login_Landing_page/backend/tests/integration/multiFileRoute.test.js` runs the
real orchestrator handler offline with two synthetic uploads and a recording transport, and
asserts the outgoing URL, two independently identified `source_documents`, both documents'
structured employment and education records, and that the combined text equals the ordered
evidence. `Login_Landing_page/src/services/__tests__/multiFileRequest.test.ts` asserts the
URL the browser picks.

The Imaginator's own `POST /api/analysis/multi-file` — the handler with no correction, no
preservation and no capture — is **not** on the website's path. Its tests are now named
`tests/test_local_multipart_handler.py` rather than `test_multifile_measurement.py`, and
they no longer claim to be multi-file acceptance.

Routing has not changed since it was introduced: `git show 56517b8:backend/server.cjs`
already calls `${imagBase}/analyze`, and `git log -S` finds no commit that retargeted it.

## What the routing question exposed, and what was fixed

Because both paths end at `/analyze`, two-file traffic runs the single-document
preservation code. Measured on two synthetic resumes, that code **silently damaged** the
second document:

| Rule | Before | Consequence on two documents |
|---|---|---|
| `source_education_records` | read the first Education section | rebuilding Education **deleted the second degree** |
| `source_summary` | read the first Summary section | the second summary became an "appended proficiency list" and was **truncated** |
| `source_skills_lines` | read the first Skills section | replaced the block with **one document's** skills, and emitted `---` as a skill |

Fixed in `source_preservation.py`: the source readers now read EVERY matching section, the
education trigger fires when a source record is entirely absent, and document separators are
filtered out of skills. Evidence:

- `tests/test_source_preservation.py` section 6 — 10 unit tests, mutation-checked (reverting
  any reader to first-only makes three fail);
- `tests/test_route_two_documents.py` — 7 tests through the real `/analyze` route, including
  the capture path with two documents and a withheld-case control.

## What remains genuinely open for two files

Stated plainly, so this is not read as "multi-file is done":

1. **A writer that merges both summaries into one line is withheld**, not approved.
   `source_correction._introduces_beyond` compares a draft span against the ONE document
   each inventory item came from, so a merged line is substantiable from neither. Withheld
   is the safe outcome (the truncation above was not), but it is still a rejection.
   Pinned by `test_a_merged_two_document_summary_is_withheld_not_silently_truncated`.
2. **Cross-document transplant of a quantified bullet** between two different employers
   whose records share a figure and a qualifier is guarded only within one employer's record
   (`_employer_of`). Not exercised by a failing test because no fixture demonstrates it.
3. **No captured multi-file run with a real model exists.** Every two-document test above is
   scripted. The acceptance target at the top of this document is therefore still
   un-met — but it is now reachable, and the blockers are preservation quality, not routing.
